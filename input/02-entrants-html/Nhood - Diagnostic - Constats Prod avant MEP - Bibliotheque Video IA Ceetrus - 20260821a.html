1. Symptôme et périmètre

Ce qui a été rapporté, par qui, quand. La Production Nhood a remis le 18/08/2026 un audit statique du dépôt au commit 4a0a724 (version applicative 1.3.0). Il conclut que « l'application peut convenir à un environnement interne, mais la chaîne actuelle nécessite plusieurs corrections avant d'être considérée comme durablement prête pour la production ». Ce qu'il porte :

  • quatre appréciations de domaine — sécurité applicative, maintenabilité, gestion des environnements, CI/CD ;
  • 6 constats de sévérité Haute, 15 autres constats (dont un de sévérité Moyenne), 8 points positifs ;
  • ses propres limites, déclarées — ni tests, ni build, ni npm audit n'ont pu être exécutés (Node/npm absents de l'environnement fourni), et aucun accès à Azure, aux règles de branche Azure DevOps ni à l'application déployée n'a été utilisé.

Ces constats arrivent dans une fenêtre contrainte : une demande CAB est en préparation pour la mise en production du 26/08/2026 (fenêtre de 30 minutes, phase de préparation le 25/08), dont le prérequis bloquant P4 exige explicitement le pipeline d'intégration continue vert sur le commit mis en production (M-38).

Périmètre instruit. Le dépôt au commit 4a0a724 dans son entier :

  • code et rendu — code applicatif, export statique, Dockerfile, nginx.conf ;
  • chaîne de livraison — les trois pipelines Azure DevOps (azure-pipelines.yml, azure-pipelines-container.yml, infra\azure-pipelines-infra.yml) et les deux pipelines Entra (infra\azure-pipelines-appreg.yml, infra\azure-pipelines-authsecret.yml) ;

3. Causes candidates

Six causes. Chacune porte les mesures qui la soutiennent ; aucune mesure du dépôt ne les contredit, et la cinquième est explicitement marquée comme hypothèse.

  • C1 — La chaîne a été construite par bascules successives, et chaque bascule a laissé son prédécesseur en place. Le produit est passé d'Azure Static Web Apps à App Service conteneur en juillet 2026, et d'un Easy Auth à secret à un Easy Auth secretless par FIC. Les symptômes les plus coûteux sont des résidus de ces bascules, pas des erreurs de conception. Soutenue par M-11, M-26, M-27, M-30, M-35.
    • la CI principale valide sans déployer, parce qu'elle déployait vers la SWA (M-11) ;
    • un pipeline de génération de secret survit à l'abandon du secret (M-26, M-27) ;
    • une configuration SWA reste dans le dépôt à côté du nginx.conf qui l'a remplacée (M-30) ;
    • la documentation décrit encore l'hébergement précédent (M-35).
  • C2 — La frontière entre « ce que le déploiement dit avoir fait » et « ce qui est servi » n'est mesurée nulle part. Soutenue par M-08, M-09, M-10, M-14, M-37.
    • l'IaC publie un output qui nomme le sujet de FIC attendu, et le pipeline qui crée la FIC ne le consomme pas : il va chercher un autre principalId par une commande Azure CLI (M-08, M-09, M-10) ;
    • aucun contrôle ne compare ensuite les réglages exigés aux réglages servis (M-14), et App Service n'a même pas de health_check_path (M-37) ;
    • c'est exactement le mode de défaillance que la factory a inscrit à l'étape MEP après le constat cockpit-ia-d1 du 19/08 (ETAPE-MEP.md §3 ter) : tout pipeline qui crée une ressource dont l'IaC a besoin lui rend son identifiant, et le déploiement dit ce qu'il a fait, la vérification dit ce qui est servi.
  • C3 — Les gates existent, mais pas sur le chemin qui déploie. Soutenue par M-04, M-12, M-13, M-21.
    • la CI principale porte gitleaks, validate:content, typecheck, lint, npm audit bloquant et le build — les points positifs de l'audit, confirmés ;
    • le pipeline qui construit et déploie l'image n'en porte aucun, et reconstruit le dépôt depuis zéro au lieu de promouvoir un artefact validé (M-12, M-13) ;
    • conséquence mesurée n°1 : les 21 tests Vitest existants ne sont joués par aucun pipeline (M-21) ;
    • conséquence mesurée n°2 : rien n'empêche de déployer un commit dont la CI est rouge — or elle est rouge aujourd'hui (M-04).
  • C4 — La cible de production a été pensée, mais l'IaC ne la connaît pas encore. Soutenue par M-18, M-19, M-36.
    • le dossier CAB décrit un environnement pr complet, tandis que l'IaC refuse par validation toute valeur autre que dev ou hpr et qu'aucun pr.tfvars n'existe (M-36) ;
    • le verrou réseau et le retrait de l'URL directe sont écrits en commentaires « étape finale » dans hpr.tfvars et n'ont pas été franchis (M-18, M-19) : la Qualif est restée dans l'état transitoire qui devait précéder le Private Link.
  • C5 — Hypothèse, non mesurée : le secretless fonctionne aujourd'hui par un chemin non documenté. Easy Auth protège effectivement Dev et Qualif, alors que le sujet de FIC et l'identité désignée par l'app setting ne se correspondent pas (M-08, M-09). Deux lectures restent ouvertes, et aucune mesure du dépôt ne permet de trancher — il faut lire les réglages servis dans Azure (R-02, étape 1). À lever avant la préparation du 25/08.
    • soit l'app setting n'est pas servi tel que l'IaC le décrit ;
    • soit une FIC supplémentaire a été posée à la main.
  • C6 — L'exigence de preuve n'a pas encore été portée dans le dossier de décision. Ce n'est pas un désaccord de fond : c'est un dossier écrit avant l'audit et non repris depuis. Soutenue par M-04, M-38, M-39.
    • le dossier CAB conclut « aucun risque spécifique identifié » (M-39) alors que la Production lève six constats de sévérité Haute trois jours plus tôt ;
    • son prérequis P4 exige une CI verte (M-38) que la mesure M-04 montre rouge.

R-01 · Constat H1 (Haute) — Next.js en retard sur les correctifs de sécurité

Lecture de ce tableau : la première ligne se lit « # : 1 · Geste : Créer la branche de correctif · Commande / fichier : git checkout -b fix/deps-security-15523 · Preuve attendue : branche locale, aucun push avant revue ». Les lignes se suivent dans l'ordre, et la dernière colonne porte ce qui doit être constaté avant de passer à la suivante.

  • Recommandation — porter Next.js en 15.5.23 et neutraliser postcss et sharp par des overrides : c'est la seule combinaison mesurée qui rend le gate vert. Effort 0,5 j. Exclut la montée majeure en Next 16, à instruire séparément. Mesures : M-02, M-03, M-04, M-05, M-06, M-07.

Ce que dit la Production. Le lockfile utilise Next.js 15.5.19 ; la release de sécurité de juillet 2026 demande au minimum 15.5.21. L'exposition est jugée réduite parce que Next.js ne tourne pas dans le conteneur final, mais il reste utilisé pendant le build et fournit le JavaScript client. Action demandée : passer au minimum à 15.5.21, régénérer le lockfile, puis exécuter npm audit, les tests et le build.

Ce que montrent les mesures. Le constat est exact et son urgence est sous-estimée.

  • Le gate est rouge aujourd'hui — npm audit --audit-level=high, que la CI exécute déjà de façon bloquante, rend exit 1 avec 6 vulnérabilités « high » sur le commit 4a0a724 : trois d'outillage (brace-expansion, js-yaml, nanoid), trois de Next.js et de ses dépendances (next, postcss, sharp) — M-04.
  • Le prérequis CAB n'est donc pas tenable en l'état — P4 exige ce pipeline vert sur le commit mis en production (M-38).
  • L'action telle qu'écrite ne suffit pas — le relèvement de Next.js seul, même à 15.5.23 qui est la dernière version publiée de la ligne 15.5 (M-03), laisse les 6 mêmes vulnérabilités : npm ne propose alors que next@16.3.1, changement majeur, pour solder postcss et sharp (M-05).
  • La combinaison qui rend le gate vert est mesurée — next@15.5.23 + overrides postcss ^8.5.26 et sharp ^0.35.3 + npm audit fix pour l'outillage : « found 0 vulnerabilities », exit 0 (M-06).
  • Elle a été rejouée de bout en bout — sur une copie du dépôt : npm ci, next build (15 pages, export produit), tsc --noEmit, next lint et les 21 tests Vitest passent tous (M-07).
